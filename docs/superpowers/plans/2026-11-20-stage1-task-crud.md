# Stage 1: Task CRUD Foundation (Implementation Guide)

> **Guided build:** You write all the code. Each task gives you the goal, the concepts (with Spring Boot comparisons), exact commands, the tests to write, and a "done when" checklist. Hints are collapsed: open one only after you've tried for a while. When you finish a task, commit and ask Claude to review it before moving on.

**Goal:** A Task CRUD REST API on ASP.NET Core 10 + EF Core + Postgres, covered by integration tests and usable in Swagger UI.

**Architecture:** One API project with folders for each layer (Controllers → Services → `AppDbContext`), plus an xUnit test project. Integration tests run the real app in memory (`WebApplicationFactory`) against a throwaway Postgres container (Testcontainers).

**Tech stack:** .NET 10, ASP.NET Core controllers, EF Core 10 + Npgsql, Postgres 17 (Docker), Swashbuckle Swagger UI, xUnit, Testcontainers.

**Spec:** [`docs/superpowers/specs/2026-11-20-stage1-task-crud-design.md`](../specs/2026-11-20-stage1-task-crud-design.md)

**C# vs Java cheat sheet for this stage:**

| Java | C# |
| --- | --- |
| `package com.x;` | `namespace TaskManager.Api.Services;` (file-scoped, one line, no braces) |
| `import` | `using` |
| getters/setters, Lombok | properties: `public string Title { get; set; }` |
| `CompletableFuture<T>` | `Task<T>`; methods are `async` and you `await` calls |
| `Optional<T>` / `@Nullable` | `T?`, checked by the compiler |
| `List<T>` / `ArrayList` | `List<T>` / `IReadOnlyList<T>` |
| Streams `.filter().map()` | LINQ `.Where().Select()`; on a `DbSet` this becomes SQL |
| `final` field set in constructor | `private readonly` field, or a primary constructor |
| method names `camelCase` | method names `PascalCase` (`GetByIdAsync`) |

**Convention:** async methods end in `Async` (`CreateAsync`). **Exception:** controller action methods do not (see Task 6).

## Task 3: Entity, DbContext, first migration

Rather than annotating the entity (`@Column`), we configure it in `OnModelCreating` with the **fluent API**, which keeps the entity clean. Migrations ≈ Flyway scripts, except EF generates them by comparing your model to a snapshot.

Read: [EF Core getting started](https://learn.microsoft.com/ef/core/get-started/overview/first-app), [Migrations overview](https://learn.microsoft.com/ef/core/managing-schemas/migrations/), [Npgsql EF provider](https://www.npgsql.org/efcore/)

- [ ] Create `Data/AppDbContext.cs`:

## Task 5: Test infrastructure (real Postgres via Testcontainers)

**Concepts:** `WebApplicationFactory<Program>` boots your whole app in memory and gives you an `HttpClient`, like `@SpringBootTest` + `TestRestTemplate`. **Fixtures** share expensive setup: an `ICollectionFixture<T>` is created once for all test classes in a collection (≈ a static `@BeforeAll` shared across classes). xUnit creates a **new instance of the test class per test**, so the constructor acts as `@BeforeEach`. Tests in the same collection run one at a time, which is what lets us reset the database safely.

Read: [Integration tests in ASP.NET Core](https://learn.microsoft.com/aspnet/core/test/integration-tests), [Testcontainers PostgreSQL module](https://dotnet.testcontainers.org/modules/postgres/)

- [ ] Add packages to the test project:
  ```bash
  dotnet add tests/TaskManager.Api.Tests package Microsoft.AspNetCore.Mvc.Testing
  dotnet add tests/TaskManager.Api.Tests package Testcontainers.PostgreSql
  ```
- [ ] `Infrastructure/TaskManagerApiFactory.cs`: a class that extends `WebApplicationFactory<Program>` and implements xUnit's `IAsyncLifetime`. It:
  - owns a `PostgreSqlContainer` (image `postgres:17-alpine`)
  - in `InitializeAsync`: starts the container, then creates a DI scope, gets `AppDbContext`, and runs `Database.MigrateAsync()`
  - in `ConfigureWebHost`: overrides `ConnectionStrings:Default` with the container's connection string
  - exposes `Task ResetDatabaseAsync()`, which deletes all rows from `Tasks`
  - in its dispose method: disposes the container and the factory
- [ ] `Infrastructure/ApiCollection.cs`: a `[CollectionDefinition("Api")]` class implementing `ICollectionFixture<TaskManagerApiFactory>`.
- [ ] `Infrastructure/TestJson.cs`: a static `JsonSerializerOptions` with web defaults plus `JsonStringEnumConverter`, so tests read and write JSON the same way the API does.
- [ ] Write a smoke test, `Tasks/CreateAndGetTaskTests.cs`, in collection `"Api"`:
  - **Test `Database_is_reachable`:** get `AppDbContext` from a scope and assert `await db.Database.CanConnectAsync()` is `true`.
- [ ] `dotnet test` passes. The first run pulls the Postgres image, so it's slow.
- [ ] Commit: `test: add integration test infrastructure with testcontainers`

</details>

<details><summary>Hint: overriding the connection string</summary>

```csharp

    builder.UseSetting("ConnectionStrings:Default", _postgres.GetConnectionString());
```

<details><summary>Hint: the DisposeAsync name clash (xUnit v2)</summary>

`WebApplicationFactory` already has `ValueTask DisposeAsync()`, and `IAsyncLifetime` wants `Task DisposeAsync()`. C# won't allow both with the same name, so implement xUnit's one **explicitly**:

```csharp
async Task IAsyncLifetime.DisposeAsync()
{
    await _postgres.DisposeAsync();
    await base.DisposeAsync();
}
```
</details>

`await db.Tasks.ExecuteDeleteAsync();` issues a single `DELETE FROM "Tasks"`. It's EF Core's bulk delete.
</details>

<details><summary>Hint: "No route matches the supplied values" from CreatedAtAction</summary>

ASP.NET Core strips an `Async` suffix from action names by default. If your action is called `GetByIdAsync`, then `nameof(GetByIdAsync)` doesn't match the route name `GetById`. That's why controller actions are named **without** `Async`:
```csharp
return CreatedAtAction(nameof(GetById), new { id = created.Id }, created);
```
</details>

<details><summary>Hint: returning 404 or 200</summary>

Return type `Task<ActionResult<TaskResponse>>`. Then `return task is null ? NotFound() : Ok(task);`. `is null` is the idiomatic C# null check.
</details>

<details><summary>Hint: due dates without a "Z" (UTC kind)</summary>

If a client sends `"2026-12-01T10:00:00"` without a `Z`, the `DateTime` has `Kind = Unspecified`, and Npgsql throws when saving to `timestamptz`. Normalize it in the service: `DateTime.SpecifyKind(value, DateTimeKind.Utc)` when `Kind` is `Unspecified`, or `value.ToUniversalTime()` when it's `Local`. Consider a small private helper method.
</details>

## Task 7: List with filtering and pagination (TDD)

Chaining `.Where()` conditionally is the idiomatic way to add optional filters. `[FromQuery]` on a class binds query-string values to its properties, like a Spring `@ModelAttribute`.

<details><summary>Hint: optional filter + paging</summary>

```csharp
IQueryable<TaskItem> q = db.Tasks.AsNoTracking();
if (query.Status is not null) q = q.Where(t => t.Status == query.Status);
var total = await q.CountAsync();
var items = await q.OrderByDescending(t => t.CreatedAt).ThenBy(t => t.Id)
    .Skip((query.Page - 1) * query.PageSize).Take(query.PageSize)
    .Select(t => /* map to TaskResponse */).ToListAsync();
```
`AsNoTracking()` tells EF you won't modify these entities. It's faster for reads, similar to a read-only transaction in JPA.
</details>

<details><summary>Hint: newest-first test is flaky?</summary>

Tasks created within the same millisecond can tie on `CreatedAt`. The `ThenBy(t => t.Id)` makes the order deterministic, but your *test* expectation must then match it. The simplest robust assertion is that each item's `CreatedAt` is `>=` the next item's.
</details>

<details><summary>Hint: <code>?status=5</code> binds successfully?!</summary>

C# enums are just integers underneath, so `"5"` binds to `(TaskItemStatus)5` even though no such member exists. Optional hardening: in the service or a custom validation, reject values where `!Enum.IsDefined(status)`. You may add a test for it.
</details>
